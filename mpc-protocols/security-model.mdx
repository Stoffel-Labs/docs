Stoffel exposes HoneyBadgerMPC field arithmetic and a Feldman-based AVSS backend. Choosing a backend requires more than a party threshold: preprocessing correctness, network identity, completion behavior and the values exposed by commitments all matter.

This page describes the security properties and implementation boundaries of Stoffel's current MPC protocol families. The maintainers' protocol-security reference tracks implementation-level changes in more detail.

## Threshold is not reconstruction count

`n` is the number of computing parties. `t` is the maximum number of corrupted computing parties. Input/output clients do not increase `n`.

Stoffel's local/network configuration requires `n >= 4t + 1` and at least five parties. A degree-`t` Shamir sharing can be reconstructed from `t+1` correct shares, but this does not mean an unverified set of `t+1` received shares is safe to accept. Error correction needs additional distinct, authenticated evaluations.[9]

The lower-level Bracha/AVID broadcasts accept `n >= 3t+1`. That primitive threshold does not override the framework rule, and a valid configuration does not by itself guarantee that every preprocessing or recovery path completes.

## Preprocessing versus online execution

Preprocessing generates random shares, multiplication triples and fixed-point masks. Online execution consumes them to accept inputs, compute and deliver results. A reserve can allow online execution to continue temporarily after preprocessing stops; it cannot provide indefinite service once that reserve is exhausted.

The HoneyBadgerMPC paper deliberately uses optimistic, non-robust preprocessing with a robust online phase. Its offline generation can stop if a party crashes. The two phases must not be assigned the same liveness guarantee.[1]

## Asynchronous safety and liveness are different

Asynchronous safety means arbitrary message delays do not invalidate the claimed privacy, correctness or agreement. Asynchronous liveness means honest parties eventually finish despite faulty parties, assuming eventual delivery between honest participants and fair scheduling, without a known maximum delay.

A finite timeout can stop a run without producing a wrong result. This loses liveness, not necessarily safety. Conversely, reducing a quorum or reusing old material to make progress can violate safety.

The implementation uses finite operation waits, a finite ABA coin wait, bounded queues and age-based session eviction under capacity pressure. These are operational limits. Raising them does not create a proof of liveness for arbitrary finite delays. Permanent network partitions and absent required client input are outside an eventual-delivery guarantee. Standalone ABA is not integrated into the default preprocessing generators, so its coin timeout is not an additional stage of every arithmetic operation.

Randomized asynchronous agreement has expected-round bounds under its assumptions, not a fixed completion deadline. The FLP impossibility result rules out a universal deterministic termination promise for asynchronous consensus with faults.[14]

## Privacy assumptions

- MPC party-to-party and client-to-party traffic must use authenticated identities and confidential channels. Reliable broadcast is not encryption.
- Randomness must come from cryptographically secure generators. Masks and triples must never be reused, including after cancellation, a crash or restoring a backup.
- The threshold is a bound on the total corrupted party set, not a separate allowance for Byzantine parties plus another allowance for crashed parties.
- Adaptive or mobile corruption resistance, proactive share refresh and secure state erasure are not established by these backends.
- This reference does not certify side-channel resistance, constant-time execution or a formal composability theorem for the deployment.
- Your program still reveals its authorized outputs and public metadata. Repeated aggregates can disclose information; MPC does not supply differential privacy automatically.

## AVSS and low-entropy values

Feldman coefficient commitments include `C_0 = s*G`. Someone who can enumerate plausible values of `s` can test each candidate against that public point. This is unsuitable as a generic hiding commitment for salaries, ages, binary choices or other small-domain application data.[10]

Use AVSS when public commitments to cryptographic scalars are intentional. Do not infer complete DKG or threshold-signature support from share generation alone. A signing protocol must additionally establish its exact transcript, nonce, key-generation, verification and recovery requirements.

## Deployment decision

If your deployment requires formally justified malicious security, adaptive corruption tolerance or guaranteed completion under arbitrary network delay in both phases, do not treat the backend name as satisfying those requirements. Obtain a review of the exact revision, resolve the preprocessing/composition limitations above and test the real transport and material lifecycle.

For ordinary field-based application arithmetic, HoneyBadgerMPC remains the relevant backend to evaluate. For verifier-facing scalar commitments, evaluate AVSS with its commitment leakage and preprocessing constraints. Neither choice removes the need to specify who may learn each output and how retries consume fresh material.
